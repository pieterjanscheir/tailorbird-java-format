Tailorbird Java Format

A Java formatter that stitches your code together the way a tailorbird stitches its nest: carefully, and always the same way.

Get started GitHub Releases
  • IntelliJ-compatibleOutput matches IntelliJ IDEA for the target code style.
  • Every rule is a settingChange any rule in one tailorbird.yml.
  • Palantir and Google presetsStart from upstream style and tweak from there.

Tailorbird is a modified version of palantir-java-format, which is itself based on google-java-format. Unlike most formatters, it isn't one fixed style: every formatting rule is a setting in a tailorbird.yml file, so a team can choose its own layout. Without a settings file you get Tailorbird's default style, whose output matches IntelliJ IDEA's formatter for the target code style.

Tailorbird is available under the Apache 2.0 License, the same licence as upstream. See NOTICE for attribution.

Install

Tailorbird is published to GitHub Packages under these coordinates:

ArtifactCoordinates
Formatterio.github.pieterjanscheir.tailorbird:tailorbird-java-format
SPIio.github.pieterjanscheir.tailorbird:tailorbird-java-format-spi
JDK bootstrapio.github.pieterjanscheir.tailorbird:tailorbird-java-format-jdk-bootstrap

GitHub Packages needs authentication, even for public packages. Create a personal access token (classic) with the read:packages scope and add the repository to your build:

repositories {
    mavenCentral()
    maven {
        url = 'https://maven.pkg.github.com/pieterjanscheir/tailorbird-java-format'
        credentials {
            username = providers.gradleProperty('gpr.user').orElse(providers.environmentVariable('GITHUB_ACTOR')).get()
            password = providers.gradleProperty('gpr.key').orElse(providers.environmentVariable('GITHUB_TOKEN')).get()
        }
    }
}

Put gpr.user and gpr.key in ~/.gradle/gradle.properties locally. In GitHub Actions, the built-in GITHUB_TOKEN works when the job has packages: read permission.

Every release also attaches the jars to its GitHub Release, if you prefer to download them.

Using it with Gradle

The SPI classes and the main class keep their upstream names (com.palantir.javaformat.java), so the upstream Gradle plugin can load Tailorbird. Apply the plugin and point it at Tailorbird instead of the default formatter:

plugins {
    id 'com.palantir.java-format' version '<upstream version Tailorbird is based on>'
}

dependencies {
    palantirJavaFormat 'io.github.pieterjanscheir.tailorbird:tailorbird-java-format:<tailorbird version>'
}

The plugin configures IntelliJ to use that formatter. For a command-line ./gradlew format task, add the com.palantir.baseline-format plugin. With Spotless, configure palantirJavaFormat() to use Tailorbird's artifact and run ./gradlew spotlessApply.

Do not enable the native formatter (palantir.native.formatter). It downloads Palantir's precompiled binary, which does not contain Tailorbird's rules.

Using it in IntelliJ IDEA

Install the upstream palantir-java-format IntelliJ plugin. It uses the formatter version that the Gradle plugin resolves for your project, so once the palantirJavaFormat dependency points at Tailorbird, import the project in IntelliJ or run:

./gradlew idea

Make sure the plugin is enabled under Settings → palantir-java-format Settings. Reformat Code then formats with Tailorbird.

Configuring the rules

Create a tailorbird.yml, for example in config/, and add the file to the palantirJavaFormat dependencies next to Tailorbird:

dependencies {
    palantirJavaFormat 'io.github.pieterjanscheir.tailorbird:tailorbird-java-format:<tailorbird version>'
    palantirJavaFormat files('config/tailorbird.yml')
}

Every setting is optional: list only what you want to change, and everything else keeps its default. For example, to keep Tailorbird's style but write if (x), indent by 2 spaces and keep the blank lines you type:

# config/tailorbird.yml
indent: 2
spaceAfterControlKeyword: true
blankLines:
  keepTyped: true

Starting from Palantir or Google style

If you like upstream palantir-java-format and only want to change a few things, start from a preset. preset: palantir sets every rule to what upstream does (it's tested against all of upstream's test cases), and the other settings in the file change it from there. For example, Palantir's style with 2-space indentation, which upstream can't do:

preset: palantir
indent: 2
continuationIndent: 4

The presets are tailorbird (the default), palantir (120 characters, 4-space indent, 8-space continuation) and google (upstream's Google style: like palantir, with 100 characters, 2-space indent and 4-space continuation).

On the command line

For pre-commit hooks, CI scripts and other tools that run the formatter directly, use the tailorbird launcher and pass the settings file with --config. Each GitHub Release from the first one on has a tailorbird-<version>.zip and its SHA256SUMS. Unzip it, then run:

tailorbird-<version>/bin/tailorbird --config tailorbird.yml --replace src/main/java/Example.java

It needs Java 21 or later, from JAVA_HOME or the PATH. On Windows, use bin\tailorbird.bat. To build the same launcher yourself:

./gradlew :tailorbird-java-format:installDist
tailorbird-java-format/build/install/tailorbird/bin/tailorbird --config tailorbird.yml --replace src/main/java/Example.java

The launcher passes the flags that open up the JDK's own Java parser, so you don't need to set JAVA_OPTS. An invalid settings file stops with a one-line error and exit code 2.

As a Git pre-commit hook, saved as .git/hooks/pre-commit and made executable, it stops the commit when a staged Java file isn't formatted and lists the files:

#!/bin/sh
files=$(git diff --cached --name-only --diff-filter=ACM -- '*.java')
[ -z "$files" ] || tailorbird --config tailorbird.yml --dry-run --set-exit-if-changed $files

Run it again with --replace instead of --dry-run --set-exit-if-changed to fix them. The hook checks the files as they are on disk, not only the staged changes.

--palantir without --config uses a tailorbird.yml on the classpath, or Tailorbird's defaults.

Gradle, Spotless and IntelliJ all load the formatter from the palantirJavaFormat dependencies, so they all read the same file; that's why it goes there. Spotless also notices when the file changes and formats again. A few things to know:

  • Mistakes stop formatting. An unknown setting, a wrong type or invalid YAML fails with a message that names the setting and lists the valid ones, so a typo never goes unnoticed.
  • One file. If tailorbird.yml is on the formatter classpath more than once, formatting fails instead of guessing which one wins.
  • IntelliJ reads the file each time it formats, so edits apply on the next Reformat Code. Run ./gradlew idea or reload the Gradle project once after adding the file.
  • Native formatter: the native-image formatter can't read a settings file. Leave palantir.native.formatter off.

imports.groups

Import groups, in order. A package prefix such as java or com.example matches that package and everything under it; an import goes in the group with the longest matching prefix. static holds all static imports, "*" everything no other group matches; imports that match no group go last. Imports are sorted by name within a group.

Default style

Without a tailorbird.yml, Tailorbird formats as shown below. Each rule is a setting you can change; the setting is named in brackets. Compared to upstream palantir-java-format:

  • No space between a control keyword and (: if(, for(, while(, switch(, try(, catch(, synchronized( (spaceAfterControlKeyword).
  • Imports in groups: static, java, javax, org, com, everything else, with a blank line between groups (imports).
  • Continuation indent of 4 spaces instead of 8 (continuationIndent).
  • ) on its own line when parameters or call arguments wrap one per line (closingParenOnOwnLine).
  • A space inside array initializer braces: { 1, 2, 3 } (arrayInitializerBraceSpaces).
  • The body of an if, for or while without braces always goes on its own line (bodyWithoutBracesOnOwnLine); one-line blocks are expanded.
  • Try with several resources: one resource per line (tryResourcesOnOwnLines).
  • Blank lines inside code are removed (blankLines.keepTyped); class bodies get one blank line after the header and before the closing brace (blankLines.aroundClassBody), one around methods and none between fields (blankLines.betweenFields).
  • JavaDoc tag blocks are separated by blank lines and tag names get a single space after them (javadoc); JavaDoc is never wrapped.

Wrapping

Continuation lines are indented by 4 spaces. When arguments are split one per line, the closing parenthesis goes on its own line. Method chains break before each ..

    firstAccountArgument, secondInstrumentArgument, thirdQuantityArgument, fourth);

service.submit(
    builder.withAccount(firstAccountArgument)
        .withInstrument(secondInstrumentArgument)
        .build(),
    options,
    callback
);

executor.execute(
    account,
    () -> {
        run();
        run();
    }
);

List<String> symbols = orders.stream()
    .filter(order -> order.isOpen() && order.quantity() > minimumQuantity)
    .map(Order::symbol)
    .toList();

Blank lines

Blank lines typed inside methods are removed, including before comments. Classes, interfaces and nested classes get one blank line after the header and before the closing brace. Fields have no blank lines between them, also when they have JavaDoc; methods, constructors, nested types and initializers get one around them. Interface methods have none. Enums have no blank line after the header or before the closing brace.

Before

    /** The second field. */

    void run() {

        int a = 1;

        // explains b
        int b = 2;

    }
}
After
class BlankLines {

    private int first;
    /** The second field. */
    private int second;

    BlankLines() {}

    void run() {
        int a = 1;
        // explains b
        int b = 2;
    }

}

Building

You need JDK 21. The Gradle wrapper downloads everything else.

./gradlew :tailorbird-java-format:test

To try a local build in another project, publish it to Maven Local and add mavenLocal() to that project's repositories:

./gradlew :tailorbird-java-format-spi:publishToMavenLocal \
    :tailorbird-java-format-jdk-bootstrap:publishToMavenLocal \
    :tailorbird-java-format:publishToMavenLocal

CI runs ./gradlew build, which also runs Error Prone and the project's own format check, and fails when the build changes tracked files.

Adding a formatting rule

  1. Add a YourRule.input and YourRule.output pair to tailorbird-java-format/src/test/resources/io/github/pieterjanscheir/tailorbird/java/tailorbird-testdata/. TailorbirdIntegrationTest picks them up.
  2. Add the setting to TailorbirdRules (with its default) and to the table in TailorbirdConfig, so tailorbird.yml can set it.
  3. Change the formatter, usually in JavaInputAstVisitor.java, behind rule(TailorbirdRules::yourSetting), so upstream styles and their tests are unaffected.
  4. To test the non-default value, add a YourRule.yml next to the input and output files; TailorbirdIntegrationTest applies it to that test case.
  5. Run the tests. ./gradlew test -Drecreate=true regenerates the expected outputs, so review that diff carefully.
  6. Check the output against IntelliJ's formatter with the target code style: IntelliJ should leave Tailorbird's output unchanged.

Keep one rule per commit, so upstream merge conflicts are easy to trace.

Staying up to date with upstream

A weekly workflow opens a pull request when palantir-java-format publishes a new release, or an issue when the merge conflicts. You can also run it by hand from the Actions tab for a specific upstream tag or branch.

Don't use a plain git merge: Tailorbird renamed upstream's packages and modules, so every renamed line would conflict with upstream edits next to it. .github/scripts/upstream-merge.sh first gives upstream's code Tailorbird's names, then merges, so only real conflicts are left. To merge by hand:

git fetch upstream --tags
.github/scripts/upstream-merge.sh upstream/develop
./gradlew format # renamed lines can need re-wrapping; commit what it changes

When it conflicts, keep Tailorbird's rule(...) checks and apply upstream's change around them, then run git add -A && git commit --no-edit and ./gradlew format. TailorbirdPalantirPresetTest fails when upstream's formatting changed and preset: palantir no longer matches it.

README.md conflicts on every upstream change to it: keep Tailorbird's version and apply upstream's changes to docs/upstream-README.md if they matter.

Releasing

Push a version tag to build, test and publish that version. The version is taken from the tag.

git tag 1.0.0
git push origin 1.0.0

The release workflow publishes the formatter, SPI and JDK bootstrap to GitHub Packages and creates a GitHub Release with the jars and generated release notes.
